Blind Computer Use

Language agents that reverse-engineer software use it better than agents that watch the screen

Published

November 2026

TL;DR

We find that a language agent given only a program's binaries and a reverse-engineering toolkit can build its own tools for that program, with no source code, documentation or internet access. Using those tools, it does far better than an agent that operates the screen. On a FreeCAD editing task, Kimi K2.6 with its own MCP server was 10× faster and used 57× fewer tokens. It passed all 13 checks, while computer use ran out its 40 minutes at 2 of 13. Across five FreeCAD tasks, it passed 87% of checks against 33%. On a real-time task, a 60-second round of Fruit Ninja, DeepSeek V4.1 Flash scored 1268 with its own MCP and 16 with computer use. Without the toolkit or access to the program, the MCP servers agents build fail on their first call.

Computer use lets a language agent operate software the way a person does, by reading screenshots and moving a mouse. On our five FreeCAD tasks, Kimi K2.6 took 142 minutes and 66M tokens this way and passed 33% of the checks. Typed tools, such as an MCP server, would be a better interface, but most desktop software does not ship one.

We ask whether an agent can build that interface for itself, starting from nothing but the program's binaries. We give it REA, a reverse-engineering toolkit for inspecting binaries and instrumenting running processes, and we withhold source code, documentation and internet access. The agent studies the program, writes an MCP server, and from then on works through that server instead of a screen. We call this blind computer use.

Giving up the screen means giving up the one interface every program has, so it is not obvious that this should work. We find that it works better, and we try to explain why.

How agents build an MCP from binaries

Our goal is to produce, from a program's binaries alone, an MCP server that another agent can use to get work done in that program. We give a single agent session the binaries and REA in an offline sandbox and ask it to build the server. The build has four steps (Figure 1):

  1. Analyze. The agent inspects the package to find what the binaries expose.
  2. Test. It tries out its guesses on the running program.
  3. Build. It writes the MCP server.
  4. Check. It runs the server against the program. If a check fails because of a bug, it goes back to step 3 to fix the code. If the failure raises a new question about the program, it goes back to step 2 to test it.

We intentionally withhold the documentation and run the build offline, so that any new information the agent gets about the program comes from the program itself. We also hide the benchmark tasks, so that the server is not tailored to them and the agent has to decide for itself what the interface should cover.

What an agent learns while building

To see where the effort goes, we look closely at one build. GLM-5.3 finished in 18 minutes and 152 tool calls, against a three-hour budget. Two thirds of those calls went to testing the program, and writing the server took 7 calls and about 20 seconds. The hard part of building an interface turns out to be finding out how the program behaves, not writing the code.

Six facts found by experiment

The findings below show what that testing produced. They are properties of this particular FreeCAD build and of how Debian packaged it, so they are unlikely to appear in anything the model has read. Each one changed the server.

How a tool call reaches FreeCAD

We then ask what kind of interface the agent ends up building. Its server starts FreeCAD, attaches with Frida, and injects a small script, and each tool call becomes a few C API calls on FreeCAD's own Python interpreter. The server stays thin because the agent does not reimplement any CAD logic: FreeCAD does the modelling and writes the files.

How agents work with the MCPs they built

To test whether these MCPs are useful, we freeze each one after its build, so that the agent using it cannot change it, and give it to the same model along with five FreeCAD tasks the builder never saw. The tasks range from a nine-check plate edit to a two-part enclosure release with 26 linked features, so that we can see whether the result holds as tasks get longer. Each task starts from an existing project file, which already passes a few of the checks.

Experiment 1

Do built MCPs beat computer use?

We first ask whether an agent does better with the MCP it built than with computer use. We give Kimi K2.6 each of the five tasks twice, once with its own MCP and once with computer use, so that any difference comes from the interface and not the model. A judge then scores the saved files against each task's checks. With its own MCP, Kimi passed 87% of checks. With computer use it passed 33%. On four of the five tasks, computer use ended at the starting file's score, so it made no measurable progress. The MCP was also cheaper: 62 minutes and 10.7M tokens for all five tasks, against 142 minutes and 65.8M.

Lid-vent (Demo 1) shows the difference on a single task. The MCP run passed all 13 checks in 4 minutes with 0.3M tokens. The computer-use run spent its full 40 minutes and 17.2M tokens and ended at 2 of 13. With typed tools, the agent spends its steps on the task rather than on finding the right field to click.

Does the gap hold on a long task?

A longer task gives small errors more chances to compound, so we also look at the enclosure release, which has two parts, 26 linked features, 21 checks and a 90-minute deadline. GLM-5.3's MCP passed all 21 checks in each of its three attempts, taking 79 seconds on average. Kimi's MCP passed 18 of 21 in 16 minutes. Its computer-use run stopped after 47 minutes at 2 of 21, the starting file's score.

Experiment 2

Is the model's prior knowledge enough?

FreeCAD is popular and its Python API is widely documented, so the model may already know much of what it needs. If so, the results above could reflect what the model memorized rather than what it found out. Our goal here is to measure how far that prior knowledge goes. We rerun the build with the same prompt and sandbox but intentionally withhold REA and the target files, so that the model's memory of FreeCAD is the agent's only source of information about it. The agent cannot inspect or run FreeCAD, but it can still write code, build its image and list its tools.

GLM-5.3's memory-only MCP never got past the starting file, and Kimi's scored 27%, below its own computer-use run. With REA, the same two models reached 100% and 87%. This suggests that knowing the API is not enough on its own to build a working server.

We also want to know whether the servers built with REA rest on what the agent observed or on what the model remembered. We match the FreeCAD names in each server's code against what the agent saw through REA during its build. Most names in the REA-built servers were observed, 79 of 87 for GLM-5.3 and 51 of 63 for Kimi. An observation does not rule out that the model knew a name beforehand, but it does mean the name was checked against the program.

Where the memory-only MCPs break

To understand why these scores are so low, we look at the first failure of each memory-only MCP. Both broke on the first call of every task, and both broke before any FreeCAD API was called. Each bug would have shown up the first time the server was run against the program. These builds had no way to test what they had written.

Can built MCPs handle real-time tasks?

CAD tasks let an agent take its time. In a real-time game, the time the model takes to reply is part of the score. Our goal here is to test whether an agent can build an interface that works under that pressure. We package a remake of Fruit Ninja as a binary with no API, and give DeepSeek V4.1 Flash the same build loop and REA. In 29 minutes and 146 turns, it reads the game's logic out of the binary, probes the live page through an adapter it wrote, and produces an MCP with four tools. We freeze that MCP and play one 60-second round with it, and one with the same model using computer use (Demo 2). Both rounds use the same seed, so that differences between them do not come from the game's randomness.

The MCP scored 1268 points and computer use scored 16. The MCP sliced 328 of the 346 fruit that spawned. Computer use sliced 16 of 158 and let 138 fall.

How the MCP plays

A model that needs 0.39 seconds or more to reply cannot react to each fruit itself, so something faster has to do the reacting. The agent's answer was to put that loop inside the tool. The game does not expose its state, so the MCP works out what is on screen from the page's drawing calls, using what the builder learned from the binary. Each slice call then predicts where the fruit are going, plans one stroke through a chain of them that avoids bombs, and carries it out as a single mouse path.

During the round, the player model made 51 calls and spent 452 reasoning tokens in total. Forty-eight of those calls were slice with empty arguments. The model decided when to slice, and the tool decided what to slice and how. Most of the reasoning had moved from play time to build time.

Where the 1268 points come from

The MCP sliced about 20 times as many fruit as computer use but scored about 79 times as many points, because the game rewards sustained play. All 48 strokes sliced at least three fruit within the game's 0.34-second combo window, so slices brought 636 points and combos another 632. The 20th slice, 6.8 seconds into the round, started frenzy mode, which doubles points and the fruit supply and clears the bombs. The MCP kept slicing more than 20 fruit every 6 seconds, which kept frenzy going to the end of the round. Computer use did not reach frenzy and played at the base spawn rate with bombs on screen.

What changes when an agent builds its own interface

Computer use asks the agent to work out how a program behaves during the task, and to pay for that at every step. A blind agent works it out once, during the build, and then reuses the result. We think this is the main reason for the gap. The Fruit Ninja player spent 452 reasoning tokens during its round because the thinking had already been done in the 29 minutes before it.

The memory-only builds show what that earlier work needs. Kimi's memory-only server contained correct FreeCAD calls and still failed on its first request, while two thirds of the calls in GLM-5.3's successful build were spent testing the program. In our reading, what matters most is that the agent can be wrong early and find out.

We tested only two applications, Kimi ran each FreeCAD task once per condition, and each Fruit Ninja condition is a single round. Our memory-only control withholds both REA and the program, so it does not separate the value of reverse engineering from the value of being able to run the program. The agent may also benefit from what the model already knows about FreeCAD, although the memory-only builds suggest that this alone is not enough.

What we are testing next

To see whether the approach generalizes beyond these two applications, we are running the same build-then-use setup on JVM and web-service applications. To see how much documentation adds, we are also running it on software where the agent is allowed to read the documentation.
