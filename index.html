Software in, MCP out:

LLM agents can reverse-engineer an application into its own MCP server

Published

November 2026

TL;DR

We find that LLM agents are surprisingly good at turning an application they can only observe from the outside into an MCP server for it. We give an agent the installed binaries of FreeCAD and REA, a reverse-engineering toolkit exposed as MCP tools, and nothing else: no source, no documentation, no network, and no idea which tasks it is building for. The agent analyzes the binary, tries things on the running program, writes an MCP server, then checks and refines it on its own. One build took 18 minutes and produced 19 tools that run inside FreeCAD's own process.

The MCPs agents build this way work. With the MCP it built, Kimi K2.6 passes 87% of task checks, against 33% through FreeCAD's GUI, using less than half the time and one sixth of the tokens. GLM-5.3 with its own MCP passes every check on all five tasks.

Take REA away and the MCPs fail. Built from the model's memory of FreeCAD alone, GLM-5.3's MCP makes no progress past the starting file on any task, and Kimi's scores below the GUI.

An application no longer has to ship an MCP server for agents to use it well. Given the binary, an agent can build one.

If you wanted an agent to use a desktop application it has never seen, with no API documentation and no MCP server, what would you give it? Today the answer is screenshots and a mouse. It works, slowly. On five FreeCAD tasks, Kimi K2.6 spent 142 minutes and 66 million tokens in the GUI and fully finished one task. An MCP server changes the picture: the agent gets typed tools for what the application can actually do. The catch is that someone has to write that server, and most software doesn't have one.

So we let the agent write it, starting from the application as shipped. It gets the binaries and REA, a reverse-engineering toolkit that exposes binary inspection and Frida-based runtime instrumentation as MCP tools. From there it has to work out how to drive the program from the outside, build a server around that, and prove to itself that the server works.

In this post, we show three things:

  1. Agents can build an MCP from binaries alone. We describe the build loop as a reusable tool, then follow one complete build of FreeCAD's MCP, minute by minute.
  2. The MCPs they build beat the GUI. In Experiment 1, Kimi K2.6 passes 87% of task checks with the MCP it built and 33% through the GUI.
  3. Reverse engineering is what makes them work. In Experiment 2, the same builds without REA produce MCPs that fail on their first call.

Software in, MCP out

The tool is one agent session running a four-step loop in an offline sandbox. It analyzes the package to find places where an outside program could take control. It looks things up or tries them, learning how the program behaves from documentation where that exists and from small experiments on the live process. It builds an MCP server from what it observed, choosing the tools and their names itself. And it checks and refines the server against the real program, going back to fix code or run new experiments when something breaks.

We run it in a deliberately hard setting. Documentation is off in every run in this post, so what the agent knows about FreeCAD it either remembered or found by trying. The builder also never sees a task: step 4 runs on test workflows the agent writes itself, and the benchmark tasks arrive only after the MCP is frozen.

What goes in and what comes out

The input describes what the software is, never what to build. The output is a directory the agent writes and a runnable image. A client of the finished MCP sees only its tool list, so usage guidance has to live in the tool descriptions.

Input, read-only

/input/
  software/       .deb packages, binaries only
  manifest.json   package + ELF SHA-256,
                  platform, launch command

Output, written by the agent

/output/
  mcp/            server, agent, launcher
  env/Dockerfile  image, built offline
  intermediate/   REA calls + responses,
                  probe scripts + SHA-256
  docs/README.md  build, run, tools, limits

Run the result

docker run -i --cap-add=SYS_PTRACE \
  -v "$WORK":/workspace -v "$EVIDENCE":/evidence  "$IMAGE"

Every MCP the loop delivers:

  • runs the application's own binary, exactly as shipped;
  • executes each operation inside the application's process, through instrumentation the agent discovered;
  • takes data as arguments, never code;
  • is built offline, within a three-hour budget.

How does an agent build an MCP from binaries?

Here is GLM-5.3 building FreeCAD's MCP. The whole run took 18 minutes and 152 tool calls, well inside its three-hour budget. Two thirds of those calls went to step 2: eleven probe scripts and a series of REA sessions against a live FreeCAD process. Writing the server itself took 7 calls. The quotes are the agent's own messages from the run, unedited.

What it learned by trying

Much of what made the server work is not written down anywhere. It is how this particular build behaves: how Debian packaged it, what its libpython exports, which calls crash it. The agent found each of these by running an experiment, and each one changed the design.

How a tool call reaches FreeCAD

The finished server has two parts. A Node process speaks MCP over stdio, starts FreeCAD under a PTY, and attaches to it with Frida. An agent script it injects runs inside FreeCAD and performs every operation through the CPython C API: import a module, read an attribute, call a method with data arguments. No Python source is ever evaluated, and FreeCAD writes every file itself.

Can agents do real work with the MCPs they build?

The real measure of an MCP is the work an agent can do with it. After each build we freeze the MCP into an image and hand it to an agent with tasks the builder never saw. The same model builds the MCP and then uses it.

Software
FreeCAD 0.20.2 on Debian 12 (x86-64), original binaries.
Build
One agent session per MCP, three-hour budget, offline sandbox. It gets the .deb packages, a manifest, REA, and a sandbox controller (shell, file writes, offline image build, smoke test). It does not get source, docs, examples, the network, or the tasks.
Memory only
Same prompt and sandbox, with REA and the target files withheld. The agent can still write, build and smoke-test an MCP; it cannot inspect or run FreeCAD.
Use
The task agent sees only the frozen MCP's tool list. The GUI condition gets screenshots, mouse and keyboard on the same FreeCAD, and code typed into consoles is blocked.
Scoring
After the run, an independent judge inspects the saved project and the exported files and checks 9 to 21 criteria per task. A task is fully done when every criterion passes. The untouched starting file already passes a few criteria, such as protected reference objects.

Experiment 1

Does an agent do better with the MCP it built than with the GUI?

Kimi K2.6 built its own FreeCAD MCP through the same loop and then ran all five tasks with it. We compare that against the same model working FreeCAD's GUI.

With its own MCP, Kimi passes 87% of checks and fully completes 3 of 5 tasks. Through the GUI it passes 33% and completes 1. On four of the five tasks, the GUI run ended with exactly the score of the untouched starting file. The MCP run needed 62 minutes and 10.7 million tokens for all five tasks; the GUI run used 142 minutes and 65.8 million. On lid-vent, the MCP run finished in 4 minutes with 51 tool calls; the GUI run used its full 40 minutes. With typed tools, the agent spends its steps on the task itself instead of on finding the right field to click.

Experiment 2

What happens without REA?

Frontier models have read plenty about FreeCAD. Do they need to probe it at all? To find out, we rerun the build with the same prompt and sandbox but withhold REA and the target files. The agent can still write code, build its image and list its tools. It just can't look at FreeCAD or run it, so everything it knows comes from training.

Without REA, neither model builds a working MCP. GLM-5.3's MCP with REA passes every check on every task, in all 15 attempts. Its memory-only MCP makes no progress past the starting file on any task. Kimi's drops from 87% to 27% of checks, below its own GUI score.

The servers also differ in where their knowledge came from. We list every FreeCAD-defined name in each server's code (types, properties, functions) and check whether it appears in something the agent observed through REA during its build.

Why the memory-only MCPs fail

We traced each memory-only server to the first step where it breaks.

Knowing the API was not the bottleneck. Kimi's memory-only server already called the right FreeCAD functions. What memory cannot give an agent is contact with the running program: how it starts, which calls crash it, and whether its own server answers a request. REA gives the agent that contact, and the agent gets it before any task arrives.

What comes next?

In this post, an agent turned FreeCAD's binaries into a working MCP server in 18 minutes, and Kimi K2.6, using the MCP it built the same way, did far better than through the GUI. We believe this changes who has to write MCP servers. An application does not need to ship one: an agent can build it from the application itself.

  • More software. We are taking the same build-then-use protocol from FreeCAD to native desktop, JVM and web-service applications, with a task-blind builder and one state-based verifier for both MCP and GUI runs.
  • The docs lane. Every run here kept documentation off, so step 2 ran on experiments alone. For software that ships a manual or an SDK, reading it first should make probing cheaper and the tools broader.
  • Build once, use many times. A build takes minutes and is paid once per software version. Every task after that reuses the frozen MCP.
