Software In, MCP Out

Reverse apps into MCP servers via LLM agents

Published

November 2026

TL;DR

Hand an LLM agent the binaries of FreeCAD and a reverse-engineering toolkit, and 18 minutes later it returns a working MCP server, built without source code or docs. With the MCP it built, Kimi K2.6 finishes 3 of 5 CAD tasks where computer use finishes 1. On our longest task, a two-part enclosure with 26 linked features, GLM-5.3 passes all 21 checks in 79 seconds on average. On a browser Fruit Ninja, DeepSeek V4.1 Flash built its own MCP in 29 minutes, then scored 1268 points in a 60-second round where computer use scored 16. Take the toolkit away and let the model build from memory, and its MCP fails on the very first call.

Through computer use, with screenshots, mouse and keyboard, Kimi K2.6 needed 142 minutes and 66M tokens for five FreeCAD tasks and finished one of them. An MCP server would give it typed tools instead, but FreeCAD doesn't ship one, and most desktop software doesn't either. So we asked the agent to build one from the installed binaries. It gets REA, a reverse-engineering toolkit that exposes binary inspection and Frida instrumentation as MCP tools, and no source, documentation or network.

The build loop

One agent session runs the loop in an offline sandbox. It analyzes the package, looks things up or tries them on the running program, builds a server, and checks the server against the program, going back a step when a check fails. Documentation is switched off in all of our runs, so the agent learns about FreeCAD only by trying. It also never sees the benchmark tasks.

What goes in and what comes out

Input, read-only

/input/
  software/       .deb packages, binaries only
  manifest.json   package + ELF SHA-256,
                  platform, launch command

Output, written by the agent

/output/
  mcp/            server, agent, launcher
  env/Dockerfile  image, built offline
  intermediate/   REA calls + responses,
                  probe scripts + SHA-256
  docs/README.md  build, run, tools, limits

Run the result

docker run -i --cap-add=SYS_PTRACE \
  -v "$WORK":/workspace -v "$EVIDENCE":/evidence  "$IMAGE"

One build, from the logs

GLM-5.3 finished this build in 18 minutes and 152 tool calls, against a three-hour budget, and spent two thirds of the calls on step 2. The quotes are the agent's own messages.

What it learned by trying

These six facts are about this particular FreeCAD build and how Debian packaged it. The agent found each one by experiment and changed the server because of it.

How a tool call reaches FreeCAD

The Node server starts FreeCAD under a PTY, attaches with Frida and injects agent.js. A tool call then turns into a few C API calls on FreeCAD's own interpreter. No Python source is evaluated, and FreeCAD writes the files itself.

Results

After each build we froze the MCP and gave it to the same model, along with five FreeCAD tasks the builder never saw. They range from a nine-check plate edit to a two-part enclosure release with 26 linked features.

Experiment 1

Kimi K2.6 with its own MCP vs computer use

We expected the MCP to help, but not by this much. With the MCP it built, Kimi passed 87% of checks and finished three of five tasks. With computer use it passed 33% and finished one. On four of the tasks the computer-use run ended at the starting file's score. Across all five, the MCP runs took 62 minutes and 10.7M tokens, against 142 minutes and 65.8M.

The long task

The enclosure release is our longest task. It has two parts, 26 linked features, 21 checks and a 90-minute deadline. GLM-5.3's MCP passed all 21 checks in each of its three attempts, in 79 seconds on average. Kimi's MCP passed 18 of 21 in 16 minutes. Its computer-use run ended after 47 minutes at 2 of 21, the starting file's score.

Experiment 2

Without REA

For this ablation we reran the build with the same prompt and sandbox but withheld REA and the target files. The agent could still write code, build its image and list its tools, with only the model's memory of FreeCAD to go on. We expected these memory-only MCPs to land well above computer use, since FreeCAD is popular and its Python API is widely documented. They did not. GLM-5.3's memory-only MCP never got past the starting file, and Kimi's scored 27%, below its own computer-use run. With REA, the same two models reached 100% and 87%.

We also matched the FreeCAD names in each server's code against what the agent observed through REA during its build.

Where the memory-only MCPs break

Both broke on the first call of every task.

Fruit Ninja

The second app is a real-time browser game. We packaged a remake of Fruit Ninja, 855 lines of HTML with no API, and gave DeepSeek V4.1 Flash the same build loop. In 29 minutes and 146 turns it read the shipped game code, probed the live page through an adapter it wrote, and handed off an MCP with four tools. We froze that MCP and played one 60-second round with it on a fixed seed, against the same model using computer use.

The MCP scored 1268 points. Computer use scored 16. It sliced 328 of the 346 fruit that spawned, while computer use sliced 16 of 158 and let 138 fall.

How the MCP plays

The game keeps its state inside a closure, so the MCP rebuilds it from what the page draws. Its adapter wraps the page's Canvas 2D calls, and the builder worked out what each call means by reading the game code. A 320×320 drawImage is a fruit, a fillRect with a 0.43 : 0.26 aspect is a bomb's fuse, and each clearRect closes a frame. Every slice call then runs six steps and sends one native mouse path.

In the round, the player model made 51 calls and spent 452 reasoning tokens in total. Forty-eight of those calls were slice with empty arguments. The model chose when to slice, and the MCP chose every target and every point of every stroke.

Where the 1268 points come from

All 48 strokes sliced at least three fruit inside the game's 0.34-second combo window, so each one earned a combo bonus. Slices brought 636 points and combos another 632. The 20th slice, 6.8 seconds into the round, switched on frenzy mode, which doubles points and the fruit supply and clears the bombs. The MCP kept slicing more than 20 fruit every 6 seconds, so frenzy never ended. Computer use sliced 16 fruit in the whole round, never reached frenzy, and played at the base spawn rate with bombs on screen.
